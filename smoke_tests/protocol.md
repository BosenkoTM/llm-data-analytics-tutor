# Протокол смоук-тестов

Методика быстрой проверки работоспособности ядра. Проверки выполняются в порядке следования
зависимостей: от инфраструктуры к прикладным сервисам.

## Порядок запуска (обобщённо)

1. Убедиться, что запущена инфраструктура: СУБД PostgreSQL с расширением pgvector и локальный
   сервер моделей (Ollama).
2. Запустить слой MCP.
3. Запустить агентов (Тьютор, Ассистент).
4. Запустить набор смоук-проверок из служебного скрипта префлайта.

> В командах используются плейсхолдеры вместо реальных значений: хост — `<host>`,
> порт — `<port>`, ключ — `<api_key>`. Реальные параметры задаются в приватной конфигурации.

Пример обобщённого запуска (иллюстративно, без реальных параметров):

```bash
# префлайт бэкенда (проверки 1–5)
python -m smoke.preflight --host <host> --port <port>
```

## Перечень проверок и критерии PASS/FAIL

### 1. Health-checks бэкендов

Проверка доступности сервисов-агентов и слоя MCP по служебному эндпоинту состояния.

- **PASS:** каждый сервис отвечает успешным статусом в пределах таймаута.
- **FAIL:** сервис недоступен, отвечает ошибкой или превышает таймаут.

### 2. Discovery / доступность MCP-инструментов

Клиент подключается к слою MCP и запрашивает список инструментов (`tools/list`).

- **PASS:** обнаружены ожидаемые инструменты (`validate_code`, `generate_task`,
  `write_trace`, `grade_submission`).
- **FAIL:** список пуст, соединение не устанавливается или отсутствует хотя бы один ожидаемый
  инструмент.

### 3. Retrieval из RAG-базы

Тестовый запрос к базе знаний по известному курсу.

- **PASS:** возвращён непустой набор релевантных фрагментов с корректными метаданными курса.
- **FAIL:** пустой результат при заведомо наполненной базе, ошибка подключения к хранилищу
  или несовпадение размерности эмбеддингов.

### 4. Инференс локальной LLM

Короткий тестовый запрос к локальной модели.

- **PASS:** модель возвращает непустой связный ответ в пределах таймаута.
- **FAIL:** модель не загружена, отвечает ошибкой или превышает таймаут.

### 5. Запись трассы `λ(d)`

Запись тестового (синтетического) события в журнал `lambda_trace_log` через `write_trace` и
проверка его наличия.

- **PASS:** запись успешно добавлена и читается обратно; поля трассы заполнены.
- **FAIL:** запись не выполнена (ошибка БД, недоступность таблицы) или прочитанная запись
  неполна.

## Итоговый критерий

Прогон считается успешным (**PASS**), если **все** пять проверок прошли. При любом FAIL
прогон помечается как неуспешный, а сломанное звено локализуется по номеру проверки.
