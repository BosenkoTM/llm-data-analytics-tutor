# 06. Журнал верифицируемой оркестрации `λ(d)`

## Назначение

Журнал `λ(d)` (таблица `lambda_trace_log`) фиксирует размеченные события оркестрации агентов:
кто, что и почему сделал на каждом шаге обработки запроса. Он решает две задачи:

- **Прозрачность** — по журналу можно восстановить, какие агенты и инструменты участвовали в
  формировании ответа и в каком порядке.
- **Воспроизводимость и аудит** — связная цепочка записей (со сквозным идентификатором запроса
  и хешами входа/выхода) позволяет проверить корректность маршрутизации и служит источником
  метрик качества (прослеживаемость, воспроизводимость, доля шагов, прошедших контроль
  Human-in-the-loop).

Записи создаются инструментом `write_trace` (см. [04_mcp_tools.md](04_mcp_tools.md)).
Журнал является **append-only** (только добавление событий) и не содержит персональных данных
студентов и содержимого диалогов — только псевдонимизированные метаданные и хеши.

## Схема записи (поля)

| Поле | Тип | Смысл |
|---|---|---|
| `id_x` | text | Сквозной идентификатор запроса (связывает все шаги одной обработки). |
| `actor` | text | Кто инициировал шаг: `tutor`, `assistant`, `teacher`. |
| `target` | text | Цель шага: агент/инструмент/состояние (`agent`, `chat`, инструмент). |
| `reason` | text | Причина/тип шага (обобщённая метка, без содержимого). |
| `policy` | text | Политика/режим (`normal_chat`, `agent_mode`, HITL-состояние). |
| `h_in` | text | Хеш входных данных шага (не сами данные). |
| `h_out` | text | Хеш выходных данных шага (обеспечивает связность цепочки). |
| `event_time` | timestamptz | Время события. |
| `status` | text | Статус шага: `draft`, `approved`, `rejected`, `confirmed` и т. п. |
| `model_version` | text | Версия используемой модели. |
| `tool_version` | text | Версия инструмента. |
| `step` | integer | Порядковый номер шага в цепочке. |
| `q_from`, `sigma`, `q_to` | text | Переход состояния: из состояния `q_from` по действию `sigma` в `q_to`. |
| `run_id` | text | Идентификатор прогона (для повторов, метрика воспроизводимости). |
| `semester` | text | Учебный семестр (агрегация метрик). |

> Хранятся именно **хеши** входа/выхода (`h_in`, `h_out`), а не сами данные — это обеспечивает
> проверяемость связности цепочки без раскрытия содержимого запросов и ответов.

## Синтетический пример записи

Ниже — **синтетический обезличенный** пример одной записи журнала (реальные трассы не
приводятся). Значения хешей и идентификаторов условны.

```json
{
  "id_x": "req-0001",
  "actor": "assistant",
  "target": "grade_submission",
  "reason": "grade_draft",
  "policy": "hitl_pending",
  "h_in": "<hash:sha256:input>",
  "h_out": "<hash:sha256:output>",
  "event_time": "2026-07-01T09:15:42Z",
  "status": "draft",
  "model_version": "<model_version>",
  "tool_version": "<tool_version>",
  "step": 2,
  "q_from": "grade_work",
  "sigma": "emit_draft",
  "q_to": "teacher_hitl",
  "run_id": "run-2026-07-A",
  "semester": "2026-spring"
}
```

Следующая запись той же цепочки (`id_x = "req-0001"`) после решения преподавателя имела бы
`status: "approved"`, `actor: "teacher"`, а её `h_in` был бы связан с `h_out` предыдущего
шага — так обеспечивается прослеживаемость всей траектории обработки.
